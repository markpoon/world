World is a browser turn-based, geo-locative rpg.

Front-end is rendering in haml, hand-written CSS, coffeescript and craftyjs, with some underscorejs sprinkled on top.

Backend is Sinatra and DataMapper on PostgreSQL (SQLite for local development and tests).

Deployed on Render (see `render.yaml`): a Docker web service and a Postgres database.

## Running and configuring

Modes and feature flags live in one place, `lib/app_env.rb`. `GET /status` reports
the current environment and flags (and logs them once at boot).

| Variable | Meaning | Default |
| --- | --- | --- |
| `RACK_ENV` | `development` or `production` | `development` |
| `ENABLE_DEBUG_ROUTES` | `/binding` (Pry) and `/debug/error` | on in local development, off on a public host (Render) |
| `SHOW_ERRORS` | full stack-trace pages instead of the generic 500 page | same as above |
| `RELOAD_CODE` | `Sinatra::Reloader` | same as above |
| `SEED_DEMO_USER` | create the demo account on boot (credentials in `lib/seed.rb`) | off |
| `DATABASE_URL` | Postgres URL (SQLite in local development if unset) | |

Players sign up from the login screen (`POST /user/signup`; passwords are bcrypt-hashed).
The world is generated on demand by `lib/world_generator.rb`: terrain and buildings are a
fixed function of a tile's position, so every player sees the same map.

The terrain art for hills, forested hills and mountains is generated by
`tools/make_terrain_art.py` (see the script for how to run it).

### Smoke test

`tools/smoke.rb` creates and serialises one of each kind of record (users, characters, tiles, buildings, items, events, journeys, ...) against a throwaway SQLite file and prints a pass/fail line for each:

    RACK_ENV=development bundle exec ruby tools/smoke.rb

In the browser: arrow keys / WASD or tapping an adjacent tile move the character, lakes/seas/mountains block movement, and stepping onto a building opens a panel describing it.

## Data layer

The game used to be written for Mongoid/MongoDB. It is now plain DataMapper on
Postgres, with no compatibility layer.

* `lib/game_model.rb` - every model does `include GameModel`. It adds `id`,
  `type` (single-table inheritance), `created_at`, the `symbol`/`list`/`dict`
  column helpers, `after_build`, `inc` and `serialize`.
* Relationships are normal foreign keys (`belongs_to` / `has n`). Many-to-many
  links (character - journey, event - journey, abilities, parents and children,
  ...) are real join tables, not arrays of ids in a JSON column.
* Items belong to a character (`character_id`) or to a building (`place_id`);
  tasks belong to an event (`event_id`) or to another task (`parent_id`).
* The JSON sent to the browser is written out explicitly in each model's
  `as_json`, and pinned by `test/wire_format_test.rb`.
* The schema is created and extended on boot (`auto_upgrade!`), so deploying new
  code upgrades an existing database in place.

### Upgrading an old database

Boot the new code against the old database and it adds the new tables and
columns. The old columns are left behind unused (ids stored as JSON arrays, a
few renamed fields). To remove them:

    DATABASE_URL=postgres://... bundle exec ruby tools/drop_legacy_columns.rb          # dry run
    DATABASE_URL=postgres://... bundle exec ruby tools/drop_legacy_columns.rb --drop

It only drops columns that hold no data.

## Tests

    bundle exec ruby test/all.rb                      # on SQLite (a temporary file)
    TEST_DATABASE_URL=postgres://user:pw@host/db bundle exec ruby test/all.rb   # on Postgres

The Postgres run needs the `pg` adapter, which the Docker image has:

    docker build -t world-test .
    docker run --rm --network host -e TEST_DATABASE_URL=postgres://... world-test bundle exec ruby test/all.rb

`tools/smoke.rb` is a quicker one-file check that creates one of every kind of record.
